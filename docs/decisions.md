# Decisions

Settled questions, so they aren't re-litigated. Each says who decided and when. If circumstances change, change the entry rather than adding a contradicting one. What was *built* is in `release-notes.md`; what is *open* is in `plan.md`.

## Versioning
- **A minor release contains new features; a release of fixes is a patch, even when a fix is breaking or fails the build in new ways.** A new check that fails the build on content that was already wrong is a fix (0.10.2, 0.11.3). Nothing reaches the site until the content repo bumps the tag, so the number isn't the safeguard: say what breaks first in the release notes. (Joey, 2026-10-09)

## Scope
- **tsgen serves exactly one site** (and perhaps one very similar second). Hardcode folder roles, file names and frontmatter keys; no options, config or plugin hooks. Remove abstractions rather than adding them. (Joey, 2026-10-01)
- **Build speed is a first-class goal**: no extra pass over the corpus without a reason. Incremental builds were considered and rejected (2026-10-07): the full build takes about half a second, and a page's HTML depends on the whole link graph and every listing, so invalidation would risk stale output.
- **Expanding partials and resolving wikilinks twice per page** (once in the backlinks pre-pass, once to render) stays: the pre-pass must run before any page renders, because placeholders for hidden pages and the `planned` link class depend on every page's links. The duplicate work is about 1.3 ms of 0.5 s. (2026-10-07)
- **Failures are loud.** A content mistake fails the build; it doesn't warn. (Joey)
- **Body EJS stays** (Joey, 2026-10-12): a page body is still rendered as an EJS template when it has `<%`, which only costs the pages that use it. `partial/mt.md` (the singular/plural "Main topic(s)") and `Colophon.md` (the year) use it. Joey wants it for what it enables with partials: Wikipedia-style embeds and something like Wikipedia's old ParserFunctions (conditionals and logic in a partial), and perhaps infoboxes someday. `ejs` is also the layout's engine.

- **The code follows JavaScript Standard Style** (standardjs.com), enforced with `standard` (`npm run lint`, `npm run fix`). Single quotes, no semicolons, no trailing commas. The old double-quote, semicolon and trailing-comma style was just what Replit Agent wrote; Joey never chose it and has always preferred Standard's. Adopted 2026-10-10 in one reformatting commit, listed in `.git-blame-ignore-revs`; the built site was byte-identical apart from the two browser scripts in `template/`, which are shipped reformatted. (Joey)

## Process
- **`main` and release tags are protected, and the suite gates both** (Joey, 2026-10-20). Two GitHub rulesets: `main` takes changes only by pull request with the `test` check (lint and the full suite, `.github/workflows/ci.yml`) green and the branch up to date; no force-pushes or deletion; no required reviews (there is no one to review). The one bypass is a repository admin merging a pull request, for an emergency such as a broken CI config; a direct push to `main` is refused for everyone. Tags matching `v*` can't be moved or deleted (a mistake is a new patch release). GitHub cannot refuse a tag on a commit whose suite is red, so **we never tag one**: before tagging, confirm the CI run on that exact commit passed (`CLAUDE.md`, Releasing). The content repo's own gates (`scripts/update-tsgen.sh`) are its business.
- **tsgen's spec is not bent to the content repo** (Joey, 2026-10-20). The two are one site in practice, but tsgen treats the content repo as a separate project that conforms to it: when a tsgen change breaks the content repo's build, the content repo is fixed, not tsgen. So tsgen's CI never builds the real content (no job that checks out the content repo), and a release is gated on tsgen's own suite alone.

## Content model
- **`permalink` stays**, even for the home page: it lets Joey rename the home page. The home page is not hardcoded. (Joey, 2026-10-08)
- **A notes page with no topic page is a feature**: it builds, with a greyed Topic tab and no warning. (Joey, 2026-10-08)
- **`hidden` means "no page", except a placeholder** when a published page links to it. This is correct as it is. (Joey, 2026-10-08)
- **Old `/notes/…` URLs are not redirected**, on purpose (v0.2.0).
- **Old `/summary/…` URLs are not redirected**, on purpose. The Summaries namespace is gone and its pages live in `reference/`; the two summary categories were kept. (Joey, 2026-10-12)
- **A disambiguation page gets no notice box** (Joey, 2026-10-12). Wikipedia's notice mostly reminds editors what the page is for, and Joey is the only editor; a visitor can see that the page is a list of links to other content. The `disambiguation` frontmatter key has no special handling.
- **`unlisted` is permanent** (Joey, 2026-10-12). Nothing in the vault uses it today, but generator behavior piggybacks on it (`404`, the empty categories), and it costs nothing to keep.
- **Scripture index entries live on the commentary page** (Joey, 2026-10-12), behind a switch (hidden by default, remembered for the whole site), not on a page of their own, and the commentary page and the Scripture index don't link to each other (the sidebar's Scripture index link is enough). A separate `/interleave/{book}` page was built first and dropped: three pages per book meant three stacked menus. A commentary page must be named exactly for a Bible book, and the build fails if it isn't. The commentary's own references don't appear in the entries, since the text is right there; other pages' references to the book do.
- **Settings page: footer link only; the commentary switch stays** (Joey, 2026-10-12). `/settings` is linked from the footer, not the sidebar. A theme choice other than System lasts 12 hours unless made permanent. The switch at the foot of commentary pages stays, sharing its setting with the settings page.
- **`meta` pages are in the Scripture index** even though they are out of the random pool; `reference` and notes pages are out of the index. (Joey, 2026-10-05) **`category` pages are in the index too**, which only leaves out the reference pages (long citation tables, already a reference like the index itself) and notes. (Joey, 2026-10-09)
- **Image links:** the canonical form is the real path, `image/<file>` (or `template/<file>`), because that is what Obsidian's link picker inserts. A bare `<file>` also works; it is always unique because two assets with the same name fail the build (names are flat in `dist/asset/`). An image in any other folder, or that doesn't exist, fails the build. (Joey, 2026-10-08)
- **Partial arguments stay.** They are in real use.
- **A reference that can't exist fails the build.** A chapter or verse its book doesn't have, a range that runs backwards, or a continuation that isn't one, is checked against the verse table and fails the build, listing every one with its page and the reason; `!` opts a reference out. Joey first declined this (2026-10-08, one known mistake in 22,901 links), then asked for it the same day once the statistics page showed 19 of them (the count had been wrong: the real figure was about 15,800 references). Hidden pages are never rendered, and pages shown by `serve --show-hidden` only warn. (Joey, 2026-10-08)
- **Books of one chapter** (Obadiah, Philemon, 2 and 3 John, Jude) are written in full: `Phm 1:3` for a verse, `Phm 1` for the whole letter. A lone number is a chapter, so `Phm 3` fails the build (there is no chapter 3). Hardcode and fail fast, no ambiguity. In the output the chapter is collapsed: `Phm 1:3` reads `Phm 3`, `Phm 1` reads `Phm` (still linked to the whole chapter), which also gives an opt-in for a bare book name in these books. (Joey, 2026-10-08; this replaces the earlier rule that `Phm 3` and `Phm 1:3` are the same reference.)
- **Numbered-book abbreviations are written without a space** (`1Jn`, `2Ki`, `1Ti`). A spaced form (`1 Jn 2:2`, `2 Ki 5`, `1 Tim 3:3`) is a mistake in the content and simply doesn't link; no aliases or special cases for it. The full names (`1 John`) take the space. (Joey, 2026-10-08)
- **Unexplained abbreviations, initials and images fail the build** (Joey, 2026-10-11), on generated pages too. An all-caps word (two or more capitals, then capitals or digits) must be in `abbreviations.json` (or be a Roman numeral or divine name); initials need an `initials.json` entry keyed by initials and surname (`R.C. Sproul`, whether written `R.C. Sproul` or `Sproul, R.C.`); an image needs an `alt-text.json` entry. Deliberate all-caps words are not Joey's style and are removed from the content; the one opt-out is a `!` in front of the word (`!YES`), kept for quoted material whose emphasis can't be rewritten, and dropped from the output. Initials are always written without spaces (`D.A.`, never `D. A.`). Dotted forms such as `A.5` are not checked.
- **Roman numerals:** Joey expects them only for the WCF and the Institutes. If an all-caps word ever collides (`MD`, `DC`, `MIX`…), the cheap fix is to stop the numeral range at 99 or add a deny list. The corpus has no collision today (audited 2026-10-07), and a term in `abbreviations.json` already wins.
- **Hidden `<h2>`s before the two navs stay** (Joey, 2026-10-06): the markup should make sense without CSS (CSS Naked Day), and a hidden heading is visible there while an `aria-label` is not.

- **Commentary pages are main content, and are in the Scripture index** (Joey, 2026-10-11), labelled with the heading each reference falls under. Their outlines go in headings, whose references the linker and collector skip, so a long outline citation doesn't count. Excluding commentary from the index, or from the longest-citation records, was tried and dropped.
- **Section titles are description terms** (Joey, 2026-10-18). A topic page's old `h3` followed by a paragraph is a `<dl>`: the title a `<dt>`, its text a `<dd>` (a Main topic line is the first). A term is a heading to everything downstream (id, Scripture index section, no linked references), so the site looks and works as it did; only the markup changed. The statistics count them apart from headings, as "Description terms" (Joey, 2026-10-18). A commentary page's verse commentary is a description list too, but its terms are not headings: they are bold text, whose references are linked and collected, as before. `h3` stays for subheadings of an `h2` (the statistics page, and a handful of topic pages, followed by a blockquote or a table).
- **Colors beyond sRGB are accepted** (Joey, 2026-10-19). Several theme hues still exceed sRGB at chroma 0.16, after the earlier tuning, so on some screens the browser makes its own gamut-mapping decisions for some colors. Joey accepts that risk; nothing further is planned. To see the sRGB result, set the Mac's display profile to sRGB. Revisit only if a color looks wrong somewhere.
- **`~text~` is a markdown-it rule, not a text pass** (Joey, 2026-10-19). The old regex over the raw source paired any two tildes on one line, so it could pair across a term and its definition or across markup (`<small>` crossing an `<em>`). As an inline rule it pairs within one block, as emphasis does, and a lone tilde is a tilde. Verified on the whole vault: the output was byte-identical to the regex's.
- **Parentheses and em dashes in definitions are small text without tildes** (Joey, 2026-10-19). In a `<dt>` or `<dd>` outside commentary (commentary notes pages included: the namespace decides, as for the terms), a parenthetical is wrapped in `<small>` by the build, unless it is part of a word (`Son(s)`). In a `<dd>` an em dash starts an `<em>` and a `<small>` to the end of its `<dd>` (or paragraph), the dash included, so every dash looks the same (an earlier version left the first one out of the small, which made a later dash differ). Nothing is wrapped twice with the same extent, but a smaller `<small>` inside a bigger one is wanted, so a parenthetical inside an authored `~…~` or after a dash gets its own. A dash with nothing after it (the `: —` placeholder for an empty definition) is left as it is, and so is a term or definition that is one parenthetical from start to end (Joey, 2026-10-19: it stays full size). Commentary prose keeps its parentheses and dashes as written. Outside a definition `~…~` is still written by hand. Before this, the 10 bare parentheticals outside commentary were mistakes in the content.
- **An alias is a plain string, redirect-only, in the page's own folder** (Joey, 2026-10-19). That is how Obsidian treats `aliases`: a slash or folder in one means nothing, and a wikilink it writes for an alias points to the real file, with the alias as its text. So an alias builds a redirect at `/{page's folder}/{slug}`, plus a line in the alphabetical index, and is never a link target: `[[Alias]]` fails the build like any unknown name, and an alias containing `/` fails the build instead of being slugified into a different URL. Aliases that cross folders are not supported.
- **Tables stay as they are: no captions, and the `.table-scroll` wrapper is not made keyboard-focusable** (Joey, 2026-10-19). None of the site's tables scroll sideways today (54 tables on 9 pages, all two columns, and 52 of them hold a link, which a keyboard user can tab to anyway), so the wrapper's keyboard gap is theoretical. Captions would help screen-reader users mostly with a table's name in a list of tables; about 50 of the 54 sit right under a heading that already names them, so Joey judged them not worth a syntax (`: caption` collides with description lists) or an automatic name. The wrapper was added in 0.7.0 as a fix for wide tables; adding `tabindex` to every one would add a tab stop per table. Revisit only if a table starts to scroll, or if Joey wants tables named.
- **Bible-reference false positives are accepted** (Joey, 2026-10-19). A capitalised book name before a number links even when it isn't a citation: "Job 2 years ago" links to Job 2 and lands in the Scripture index. The `!` opt-out is the fix. Names are case-sensitive, so "I am 30" is not Amos 30. A word list for what follows the number (years, times, …) or a build failure on suspicious cases would cost more than it saves. On 2026-10-19 all 101 chapter-only matches in the vault were real citations. Revisit only if a false positive shows up.
- **Headings and terms are unique on a page, except a repeat right after the first** (Joey, 2026-10-18). An `h2` and the term under it with the same name is legal: the term takes no id, so `#name` links and Scripture index entries go to the heading. The same name anywhere else on a page fails the build as a content mistake; there are no `-2` suffixes. Prepared for `[[Page#Heading]]` links, which need a name to point to one place.
- **A term is linked with Obsidian's block id** (Joey, 2026-10-18). Obsidian can't link to a description term, only to a block, so `[[topic/Atonement#^5602cb]]` (the id Obsidian writes at the end of a definition's line) links to the term above that definition, at the id tsgen gave the term. The `^id` is never an anchor and never shows. `[[Page#Heading]]` works too, for an h2, h3 or topic term, matched by its slug (so case and punctuation don't matter). A `#` link that matches nothing fails the build.
- **Notes and commentary pages get a table of contents** of their `h2`s (Joey, 2026-10-11): bullets in a box, no `h3`s, titled "Contents" (notes) or "Outline" (commentary), and only with three or more.

## Statistics
- **The links on `/statistics` are done** (Joey, 2026-10-12). Nothing else on it is a candidate for linking.
- **`/statistics` is a generated page in the `meta` namespace**, the first one there: listed in `/index/alphabetical/meta`, linked from the sidebar, and kept out of search, the random pool and the Scripture index. (Joey, 2026-10-08)
- **Deterministic output.** No dates, no timings: the page shows the tsgen version and the content commit and is otherwise a function of the content, so builds still compare byte-for-byte.
- **What it counts.** Hidden and unlisted pages are not counted anywhere on the page, and it has no figures about them (no "N pages are hidden", no placeholder or unlisted counts). Words, links, categories and page figures count the listed pages and their notes, with notes shown separately where it matters. (Joey, 2026-10-08) The Scripture figures count exactly the references the Scripture index lists: notes pages, reference pages and categories are left out, so the page and the index can't disagree. Counting notes pages inflated the coverage (40.9% of verses against 27.2%). (Joey, 2026-10-08) Two figures do count references the index leaves out, kept apart from the index's: the overview's total (content and notes pages together; reference pages and categories are still out) and a table at the top of the Scripture section, by namespace with "On pages" and "In notes" columns, which also counts the reference pages and categories. Everything else in that section stays content-only, and "content" there means topic and commentary pages: Meta pages (About, Home) are in the Scripture index but don't count toward the cited figures. (Joey, 2026-10-09)
- **The verse table uses the KJV numbering**, which is accurate enough: modern translations keep the traditional chapter and verse numbers, and when they omit a verse they skip its number so the numbering holds. A real reference that falls outside the table fails the build. (Joey, 2026-10-09)
- **Two ideas, chapters cited and verses cited.** A chapter is cited when any citation touches it. A verse is cited only when a citation names it, alone or in a range of at most fifteen verses: `Romans 5` cites the chapter but none of its verses, `Romans 12:1–15:13` (71 verses) cites its chapters but not its verses, `Romans 5:1` cites both. The limit stops an outline that cites whole sections from "citing" most of a book (it gave Romans 97.7%; 80.8% with the limit, and the whole Bible 26.1% became 23.5%), and fifteen still credits most pericopes (the parables, Matthew 25:1–13, Ephesians 1:3–14). Ten and twenty were tried: ten dropped about 100 citations of 11–15 verse passages, and twenty let in the 16–20 verse passages Joey was content to lose (25 passages, 27 citations). A hard limit has a cliff, so a passage of 16 verses counts for nothing while one of 15 counts fully. (Joey, 2026-10-08)
- **Cost, measured 2026-10-08:** about 26 ms on a 500 ms build (+5.3%): roughly 9 ms for words (tokenizing and ranking), most of the rest for the Scripture coverage, 4.5 ms to render and emit the page, and some per-page bookkeeping. If it ever needs trimming, the most used words and the Greek, Hebrew and punctuation counts are the cheapest things to drop for the least loss.

## Template and CSS
- **The mobile footer's "· Colophon" middot is intentional**: it sets Colophon apart from the copyright. (2026-10-07)
- **`img { width: 100% }` stays**: no image in the vault is smaller than the column (the narrowest is 540px against a column of at most about 438px), and the home-page avatar is sized by its figure. (2026-10-07)
- **Every hue token in `:root` stays, used or not**, so they are ready to use. (Joey, 2026-10-07)
- **The source order of the layout stays** (Joey, 2026-10-12): the logo header, then `<main>`, then the page tabs, then the site navigation (the sidebar) and search, then the footer. It reads the same with CSS off (CSS Naked Day) and on mobile, where the sidebar is at the bottom; on desktop the sidebar sits to the right of the content, which reads as "after" it. Screen readers reach the menus through landmarks: the site navigation and page tabs are labelled `<nav>`s with visually hidden headings, and `<main>` and the search form are landmarks. There is no skip link, and none is needed for that.
- **Typekit's `font-display: auto` stays** (Joey, 2026-10-12). Conventional wisdom says `swap`, but Joey would rather the site show no text for a brief moment than flash from a fallback font to the real one, and he won't fuss to match a fallback font's proportions to the real font's. (It is set in the Adobe Fonts project, not in tsgen.)
- **WCAG is a guide here, not a requirement** (Joey, 2026-10-13). This is Joey's personal website, not a government, business or nonprofit site, and almost nobody else reads it. The accessibility work goes beyond what a personal site owes: readers who want underlines can turn them on in the settings page, and Joey will point to that page from the home page. So two known gaps are **will not fix**: links in muted text (the paragraph after an h3, footnotes) are only about 1.1:1 against the text around them, and in dark mode links sit at about 3:1 (inside `<mark>`, about 1.3:1); abbreviations show no cue that they have a `title` unless the setting is on. Both are covered by the "Underline links" and "Underline abbreviations" switches. Revisit only if Joey says so.
- **Links in the text are not underlined by default** (Joey, 2026-10-13). Joey prefers the plain look, and a settings switch ("Underline links") turns underlines on, for every link but the logo, the social icons and the page tabs (the sidebar and footer links are the same color as their text, so they are included). Claude advised underlining by default, since WCAG 1.4.1 is judged on the default state and the link colour is only borderline against body text (see `plan.md`); Joey chose the plain default knowingly. The default is `UNDERLINE_DEFAULTS.links` in `lib/layout.js`, so it is a one-word change.
- **Abbreviations are not underlined by default either, for now** (Joey, 2026-10-13). A second switch on the settings page (under "Accessibility", with the links one) gives every `<abbr title>` the standard dotted underline. Whether that should be the default is still open (`plan.md`); `UNDERLINE_DEFAULTS.abbr` in `lib/layout.js` is the one word.
- **A tap on an abbreviation shows its title in a popover, always** (Joey, 2026-10-13): on a device without hover, whether or not the abbreviation is underlined, built on the Popover API rather than `<dialog>` (a modal dialog is far too heavy for a definition). Abbreviations get **no tab stop** (hundreds per page; screen readers already get the `title`). Touch devices do **not** get the dotted underline by default to make the taps discoverable: the underline follows the preference alone. Claude had advised the underline on touch; Joey declined. An abbreviation inside a link leaves the tap to the link.
- **Sizing follows the reader's default font size, the layout scaling with the text** (Joey, 2026-10-13). The root font size is in `rem` terms (on the root, `rem` means the browser's default size), `--main-width` is `1/0.044` rem (the constant 22.7em measure, so the column grows with the text), and every breakpoint is in `em` (so the sidebar waits for a wider window at a larger default, instead of squeezing the column). The text is never smaller than the default (the `1rem` floor), which makes page zoom work on a phone. A narrow screen with a large default necessarily reflows to fewer characters per line.
- **The root size is constant at 22px from 500px wide, and the sidebar starts at 800px** (Joey, 2026-10-13: "Go big or go home"). The size used to keep growing with the window to 862px, so zooming a laptop to 200% gave only 1.65× text; now it gives exactly 2×. The cost: windows 500–800px wide (tablets in portrait, half-width desktop windows) get 22px text in a 500px single column instead of about 18px in the sidebar layout, and a phone in landscape (844px wide) shows the sidebar at 22px. Phones up to 412px wide are unchanged.
- **Head whitespace is not minified**; gzip hides it. (2026-10-07)
- **No SVG icon and no web manifest.** The feather is a Font Awesome Pro glyph (the licence bans standalone SVG copies in the repo), and a manifest would need a new 512px render, only worth it if the site should be installable on Android. Only rasterized PNGs live in `template/favicon/`. Text fonts come from Typekit, so there are no font files.
- **`theme-color` is always the nav gray** (`#585858` light, `#484848` dark), so Safari's chrome matches the sidebar at every width. (Joey, 2026-10-08) A thin light line at the top of the phone layout in Safari persists; the page itself has none, so it is presumed to be Safari's own chrome and is not ours to fix.
- **The only `!important`s** are the `.visually-hidden` utility and the print stylesheet's plain-text links, on purpose.
- **Known limitation:** the Font Awesome kit is a deferred script, so icons appear a moment after the page paints, and with JavaScript off the logo, search icon, star and the rest are absent (the search button is then an empty circle with its label).
