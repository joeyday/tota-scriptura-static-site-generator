# Plan

Open work only: bugs to fix and features to build. When something is finished, delete it here; `release-notes.md` records what shipped and when, and `decisions.md` records the questions that are settled. Verify an item against the code before acting on it, since it may have gone stale.

## Features

- **Deterministic hero assignment from a larger pool**, for `og:image` and perhaps the page's visible hero. It would replace the single fallback image. Assign deterministically (for example a hash of the page path) so a page's card doesn't change between builds. Open: where the pool lives, and whether every page should show a hero or only some (Joey is undecided; don't build the visible part until he decides).
- **More statistics, if wanted:** the page is built (see `docs/decisions.md` for what it counts). Candidates not built: external links by domain, abbreviation and Roman numeral counts (each needs its pass to return a count), build-over-build trends (needs history, and breaks deterministic output), and an "as of" date.
- **Lazy-load the Scripture index entries on commentary pages** (Joey, 2026-10-19), when a much longer book than Titus arrives. Hidden entries are still downloaded with the page; a long book's could be fetched the first time the switch is turned on instead. Also check then that the Outline and the switch hold up at that length. Fine as it is for now.

- **Combining marks only come from Source Serif.** A transliteration written as a base letter plus a combining mark (`p̄`, not a precomposed letter) joins only when Source Serif has the mark (21 of 112). Greek in a small-caps term stays lowercase, since Noto has no small caps where Source Serif made Greek capitals. Four vault files carry a stray byte-order mark (U+FEFF); `scripts/subset-fonts.py --vault vault` lists what no font covers (only invisible marks and the sandbox's emoji, today).

- **Italics and abbreviations inside a term's italic aside.** In a topic term or `h3`, the generator wraps a parenthetical's words in `<em>` (so the parentheses stay upright). Two cases in the corpus look wrong or untested: an authored italic inside the aside (`(gr. <em>pas</em>)`, the four `fourfold-state-of-man` terms) stays italic, since an `<em>` inside an `<em>` doesn't flip, so the foreign word no longer stands out; `small em em { font-style: normal }` would flip it to roman. An abbreviation inside it (`LXX` in `baptism`, `OT` and `NT` in `hell`) renders as full-size italic capitals, because Source Serif's italic has no small caps; `small abbr { font-style: normal }` would give roman small caps. Neither rule is written, and neither case has been looked at in a browser.


## The book
The generator works end to end (the book is part of every build, see the README and `docs/decisions.md`), with the 2020 book's contents, index and trim size, a preface, and Roman front-matter numbering. Open work, roughly in the order it shows:
- **Running heads and chapter-opening pages** without them: the Part on a left page, the topic on a right page.
- **The Scripture index is about 43 pages** of the 213. Options to tighten it if that is too many: run the references of a chapter together on a line, three columns at a smaller size, or merge consecutive pages (21–23). Also whether the topic index wants letter headings.
- **A colophon:** the vault's `Colophon.md` is about the typography and tools and wasn't in the 2020 book; whether it joins the generator's own pages is Joey's call.
- **For the printer:** the book has no bleed, crop marks or PDF/X profile yet, and the cover (`cover.pdf`, built from the 2020 one) is made on assumptions to check against the printer's specs: an eighth of an inch of bleed, and a spine of `PAPER` (KDP's white paper, 0.002252 in) per page in `lib/book/cover.js`. The 2020 cover was 9.17 × 7.13 in, about 0.4 in of spine and 0.135 in of bleed top and bottom. Ask the printer for specs, and check the spine text (white on the gray, black past the diagonal) still falls on the right side of the diagonal at the final spine width. Also look at the cover in print: the icon is the Font Awesome feather-pointed, 36 pt tall and 45 wide, a little larger than the old feather.
- **Copyfitting: short last pages and gaps.** Claims now break wherever two lines fit on each side (re-measure: how full are the pages that are not a topic's last, and how many topics end on a page holding a line or two?). Option: a copyfitting pass that lays the book out, finds a topic whose last page holds a few lines, tightens that topic's spacing a hair and lays it out again (two or three rounds).
- **Typesetting polish:** whether Part pages and chapter openers want ornaments, and any further hyphenation tuning.
- **Check the book on the CI runner:** the book is now made by every `tsgen` build, so the first deploy that has 0.22.0 also typesets it with the runner's Chrome. Look at that PDF (the page count may differ from a Mac's), and at the two covers made beside it from 0.23.0 (the suite already printed them, icon and all, on the runner), and decide whether to link it from the site (nothing links to `/book/book.pdf` yet; it is about 19 MB, mostly the hero images and a link annotation for every index page number, so consider downsampling the images).
- **Cold book builds and CI:** a book with nothing remembered takes about ten seconds (each section is laid out one after another in one Chrome page, with per-section overhead that the whole-book layout didn't have). Candidates: lay the sections out in several tabs at once, or lay the whole book out once when most sections are stale and slice its pages into sections. The content repo's workflow also needs `actions/cache` on `.dist-cache` (and `.dist-cache` in its `.gitignore`) for deploys to start warm.
- **The fonts' timestamps:** `scripts/subset-fonts.py` now keeps upstream timestamps, but the committed font files carry the old random ones, so the next rebuild shows every file as changed once; regenerate and commit them together when something else needs a font change anyway.

## Code

- **Review the harmony table** (`lib/bible/harmony.json`). Every row was aligned verse by verse against the KJV text, by wording that overlaps, so every row wants a reader who knows the passages. Weakest: the rows marked `~`, which match a block with a block because the tellings differ (split them where the telling lines up), the genealogies and lists of names (Genesis and Chronicles, the mighty men, Jeroboam to Hezekiah's reign summaries), where wording gives little to align on, and the Chronicles rows with loose wording (1 Kings 5 / 2 Chronicles 2, 2 Kings 12 / 2 Chronicles 24, 2 Kings 16 / 2 Chronicles 28). Not in the table, on purpose: Ephesians/Colossians, 2 Peter/Jude, Obadiah/Jeremiah 49, Isaiah 2/Micah 4.
- **Dependency updates.** Checked 2026-10-12, `npm audit` is clean and the minor and patch updates are in (`markdown-it-attrs` 4.5.0, `markdown-it-bracketed-spans` 1.0.3, `slugify` 1.6.9; the output was identical). Three are a major version behind: `ejs` 4.0.1 → 7.0.1, `markdown-it` 14.3.2 → 15.0.2 and `markdown-it-attrs` 4.5.0 → 5.0.1. Read each changelog and compare the whole site, since markdown-it and its plugins decide how every page's Markdown renders. Do them one at a time, each its own commit.
- **Speed.** The build is about half a second and Node's startup is a fixed ~50 ms, so what is left is small; measure before committing to any. Candidates: one tokenizer walk shared by all text transforms (ordering dependencies, abbr → roman/divine skip, make fusing harder), and profiling again for markdown-it (~80 ms), the layout render and reading sources. **Remember work by what it was made from** (Joey, 2026-10-23: not now, the site build is fast enough): the book's section cache could be done for the site too, a rendered page kept by a hash of its source and everything it reads. The complication is that a page reads other pages (wikilink targets and their titles, backlinks, categories, the per-namespace lists, partials, aliases), and the in-memory post-passes, the indexes, search, the Scripture index and `/statistics` read all of them, so a page's key would be its source plus a digest of the facts it reads from elsewhere, and the generated pages would still be rebuilt every time. The same rule as the book's applies: the output must be what a cold build makes. Revisit if the build grows past a few seconds.
- **Make wikilinks, `%%` comments and `^block` ids markdown-it rules.** Today `render.js` handles them with regexes over the raw source, and `maskCode` (`lib/code.js`) hides code from those passes first. As parser rules they would skip code by construction (and `[[a|b]]` in a table cell would stop being a regex question). Partials and EJS stay textual preprocessing, since they output Markdown, so `maskCode` stays for them. Only these three move; the HTML post-passes stay, because they also run on generated pages and the layout, and the Bible-ref linker needs context across inline tags. Check the whole site with `compare-dist`. The corpus has no fenced code today, so this is robustness, not a fix.

## Future phase?

Ideas from a brainstorm (2026-10-27), none of them decided. The project is going into maintenance mode, so these are here to keep, not to schedule.

- **Hover a Bible reference to see which topics cite it.** The reverse of RefTagger: a small popover built from the Scripture index, like the one for abbreviations.
- **"Name that passage" quizzes and Anki decks.** Every claim already has references attached. A static quiz page shows a claim and asks for the passage, or the other way round; the same data exported as flashcards for Scripture memory.
- **Revision history per topic.** The vault is a git repo, so the build could read its log and show when a claim was added, reworded or dropped. It needs a full clone in CI, and the output would depend on history, so deterministic builds would need thought.
- **A "make your own book" page.** The reader picks topics and gets a PDF. Paged.js runs in the browser, so it may work on a static site with no server.
- **Per-claim social cards.** A stable link for every claim and a generated image of the claim and its references, rendered by the headless Chrome the book already uses.
- **A topic constellation.** An interactive map where topics sit closer together if they cite overlapping Scripture, like Obsidian's graph view.
- **An open dataset.** A static `claims.json`, or one JSON file per passage, for Bible apps, other sites and AI tools, perhaps with a small script other sites could include to link their verses to Tota Scriptura passages.
- **Creed and confession cross-references.** Pages mapping topics to the sections of historic creeds and confessions. Mostly content work; the generator would do the indexing.
- **Per-passage pages**, built from the Scripture index.
- **Related topics by shared Scripture**, shown on each topic.
- **An EPUB** from the book pipeline. Joey's view: the web version is already the best digital version, so this is only vaguely tempting.
